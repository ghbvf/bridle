## 第 0 部分：阅读导引（金字塔顶）

### 一句话总纲

在 AI 编码以接近零边际成本生产代码的时代，治理的唯一目的是确保每一份制品在交付时刻同时处于「**被需要 / 被信任 / 被理解**」三重状态。

### 本方案的 SCQA

- **Situation（背景）**：AI 编码已经把生产端边际成本压到接近零
- **Complication（变化）**：但人类审查能力线性，AI 代码故障率约 3 倍于人工，价值/架构/知识衰减全面加速
- **Question（问题）**：如何在不阻塞 AI 产能的前提下，让组织对产物始终保持需要、信任、理解？
- **Answer（结论）**：用框架锚定边界、用声明式状态机管理生命周期、用 Harness 工程让渡 AI 自主权、用看板吸收产能冲击 —— 一切机制都从四条不可再分事实推导而来。

## 第 1 部分：第一性原理推导（推理引擎）

### 1.1 不可再分事实（4 条推导起点）

| 事实 | 表述 | 来源支撑 |
|---|---|---|
| F1 | AI 编码的边际成本趋零 | LLM 算力规模化已是产业事实 |
| F2 | 人类审查能力线性增长，无法跟随 AI 产能 | Sonar 调研：AI 代码故障率约 3× 高于人工 |
| F3 | 软件资产经历价值/架构/知识三重衰减 | 业务变化 / 依赖腐烂 / 人员流动 |
| F4 | 组织生存依赖可信资产的累积；不可信资产是负债 | 资本论"凝结劳动" + 工程实践 |

这四条无法再分解为更基本的命题——它们是 AI 编码时代的"物理学约束"。

### 1.2 由事实推导公理

- **F2 + F4** → AI 输出必须对齐意图 → 公理 1：**意图保真**
- **F2 + F3** → AI 决策必须可回滚 → 公理 2：**动作可逆**
- **F1 + F3 + F4** → 质量必须编码进系统而非事后补救 → 公理 3：**质量涌现**

### 1.3 由公理推导支柱

| 公理 | 推出的支柱 | 工程轴 | 失守的代价 |
|---|---|---|---|
| 意图保真 | **价值锚定**：业务意图持续可见 | 时间轴 | 资产腐烂为僵尸代码 |
| 动作可逆 | **边界封控**：可逆性要求边界清晰 | 空间轴 | 架构腐烂为大泥球 |
| 质量涌现 | **制程内建**：质量在系统中挤压而出 | 因果轴 | 质量腐烂为技术债 |

### 1.4 推导链的封闭性（MECE 自检）

- **两两正交**：三支柱分别在时间/空间/因果三个独立轴上工作；单一支柱崩塌产生独特失败模式（僵尸代码 / 大泥球 / 技术债）
- **共同穷尽**：组织对软件资产的全部担忧（"还在做对吗 / 它在哪 / 怎么证明做对"）都被三支柱覆盖
- **反向验证**：F1+F2 衍生出"差异化门禁 + 拉式系统"机制（第 5 部分）；F1+F3 衍生出"健康度持续监测"机制（第 8 部分）。每个具体机制都能反向追溯到事实。

> **本节回答**：本节属于推理引擎——证明三公理三支柱不是选择，是必然。

## 第 2 部分：终极目标（金字塔顶）

### 2.1 顶层结论

> **在每一个交付时刻，AI 生成的制品同时处于「被需要 / 被信任 / 被理解」三重状态。**

### 2.2 三衰减对抗模型

| 状态 | 对抗的衰减 | 衰减原因 |
|---|---|---|
| 被需要 | 价值衰减 | 业务变化 / 需求过期 |
| 被信任 | 架构衰减 | 依赖腐烂 / 熵增 |
| 被理解 | 知识衰减 | 人员流动 / 上下文丢失 |

治理的本质就是**对抗这三种衰减**。每个机制都应能回答"对抗了哪一种衰减"，否则就是冗余。

> **本节回答**：本节是金字塔顶之下的第一层结论——把一句话总纲拆为三个独立的可观察状态。

## 第 3 部分：价值视角（资本论分析）

### 3.1 C / V / M 在软件工程中的精确映射

| Marx 概念 | 传统软件工程 | AI 时代演化 | 治理含义 |
|---|---|---|---|
| **C 不变资本**（凝结劳动） | 框架 / 基础设施 / 契约骨架 / 代码库 | + 预训练模型 / 向量库 / 评估集 | C 越精密，模块产出的精度越高 |
| **V 可变资本**（劳动力） | 工程师工时 | 工程师 + AI 工具的劳动组合 | AI 是 V 的倍增器（同等 V 产出 N×） |
| **M 剩余价值**（资产沉淀） | 用户付费 + 可信代码资产 | 同上 + 评估反馈数据 | M 被三衰减侵蚀 |
| **W 总价值** | C + V + M | C + V + M | 等式不变，结构变 |

### 3.2 关键命题：AI 不是新的价值源泉

劳动价值论的核心命题：**只有活劳动（V）创造新价值**。AI 是凝结的过去劳动（属于 C），它**转移**自身价值到产品中，但不创造剩余价值。

**两个对称推论**：
- 把 AI 当作"新的程序员"是错误命题——AI 是机床，不是工人
- 高估 AI 自治 = 把 C 误认为 V → 组织失去价值创造的意识源泉
- 低估 AI 倍增 = 没用足生产资料 → 组织在产能上被对手甩开

### 3.3 框架 = 凝结度最高的不变资本

为什么阶段一必须先锻造框架？因为框架是组织最高阶架构智慧的凝结，**沿模块的批量复制无限放大**：

- 优秀框架 × 100 个模块 = 100 份高质量产出
- 缺失框架 × 100 个模块 = 100 份混乱（同样速度复制混乱）

这就是"先建机床，再上流水线"的资本论必然性。

### 3.4 治理 = 必要的监督劳动（边界条件）

按马克思的判断标准：监督劳动是"灰色地带"——是否生产性，取决于是否直接为资本积累创造价值。

**软件治理的边界条件**：

```
治理是生产性的，当且仅当：
    M_保留 = 因避免衰减而保留的剩余价值 ≥ V_治理 = 治理本身消耗的活劳动
```

**违反边界的反模式**（详见第 11 部分）：
- 治理活动占用 > 30% 工程师时间
- 资产健康度提升 < 治理投入

### 3.5 三衰减 = 剩余价值被熵增吞噬

第 2 部分的"三衰减"在资本论视角下就是：**M 被熵增吞噬**。

- 价值衰减 → 已沉淀的 M 因业务变化失去市场承认
- 架构衰减 → 已沉淀的 M 因架构腐烂需要重写
- 知识衰减 → 已沉淀的 M 因人员流动需要重新理解

治理是对抗熵增的工程化机制——它把 M 从"易腐"变为"长期"。

> **本节回答**：本节属于价值层——为后续工程层、流层、控制层提供经济判据。

## 第 4 部分：系统视角（系统工程 + 软件工程）

### 4.1 V-model 在 AI 时代的变形（核心图）

```
        左侧（AI 加速）              右侧（重武装验证）

           意图定义  ────────────────►  端到端验收
              ↓                              ↑
           架构设计  ────────────────►  集成测试 + 契约校验
              ↓                              ↑
           详细设计  ────────────────►  单元测试 + 形式化验证
              ↓                              ↑
       ┌──────────────┐                       │
       │ AI 编码(秒级) │ ─────────────►  静态分析 + 模糊测试
       └──────────────┘                       │
              ▲                                │
        【加速 100×】                  【验证重武装 3×】
```

**变形逻辑**：传统 V-model 假设左右两侧人力对称——一个开发者写一个测试。AI 时代左侧加速 100×，若右侧不重武装，**故障率必然 3× 飙升**（Sonar 调研数据）。

V-model 在 AI 时代的本质重写：**左侧编码价值 → 右侧验证价值**。验证不是事后补救，而是 V 流向 M 的核心通道。

### 4.2 ISO/IEC 15288 ↔ 模块五态机的对应

| ISO 15288 阶段 | 对应模块状态 | 治理强度 | 关键活动 |
|---|---|---|---|
| Concept | 意图卡片 | 价值评审 | 业务对齐 + 技术可行性 |
| Development | experimental → candidate | 中 | AI 加速实现 + 渐进强化测试 |
| Production | candidate → asset | 高 | 全门禁 + 兼容性承诺 |
| Utilization | asset | 持续监控 | 健康度三维评分 |
| Support | asset → maintenance | 中 | 守住兼容性 |
| Retirement | retired | 仅审计 | 墓碑机制 + 24h 软删窗口 |

ISO 15288 提供跨工业的全生命周期参照系，**让阶段不再凭感觉定义**。

### 4.3 可追溯性矩阵（双向追溯）

```
意图卡片 ──► 模块 manifest ──► 接口契约 ──► 测试用例 ──► 健康度信号
   ▲              ▲                ▲             ▲              ▲
   └──────────────┴────────────────┴─────────────┴──────────────┘
                          双向链路
```

任意一端变更都能追溯到另一端：
- 意图变更 → 哪些模块受影响？
- 健康度信号异常 → 反向追溯到哪个意图未被满足？

这是 v3 比 v2 多出来的"端到端可见性"。

### 4.4 SWEBOK v4 新增 KA 的特殊地位

SWEBOK 在 v3（15 KA）→ v4（18 KA）演化中新增三个领域：

| 新增 KA | 在 AI 时代的特殊地位 |
|---|---|
| Software Architecture | 框架（C）的载体，决定 AI 产出精度上限 |
| Software Operations（DevOps） | 见第 5 部分流视角 |
| Software Security | AI 代码 3× 故障率中相当一部分是安全漏洞 → 必须前置 |

这三个 KA 在 v3 中分别映射到双实体的"框架"、第 5 部分的"流"、差异化门禁的"安全层"。

### 5.4 利特尔法则破解 AI 产能瓶颈（核心）

**核心问题**：AI 日产 50 个函数，团队日审查 10 个 → 积压 → 漏检率飙升。

**利特尔法则公式**：

```
平均周期时间 = WIP / 吞吐量
```

**应用**：若想保持 <1 天审查周期，团队日审查能力 = 5，则 WIP ≤ 5。

**分层快速通道**（看板对 AI 时代最关键的贡献）：

- L1 低风险（90%自动化测试通过）：WIP=20，AI 主导，人抽查 10%
- L2 中风险（新特性）：WIP=10，AI 起草 + 人审查
- L3 高风险（安全/并发/外部接口）：WIP=3，专家 + 形式化验证

加权 WIP：高风险卡片占用审查时间 ×2，自动调控。

### 5.5 双环看板（拉式系统）

```
  意图环                          模块环
  ┌────────────┐                  ┌──────────────────────────┐
  │待孵化      │                  │实验 → 候选 → 资产 → 维护 │
  │孵化中      │ ────意图绑定───► │              ↓           │
  │已交付      │                  │             退役         │
  └────────────┘                  └──────────┬───────────────┘
                                             │
                          ┌──────────────────┴──────────────────┐
                          │      分层快速通道（拉式系统）        │
                          ├─ L1 低风险（90%自动 + WIP=20）       │
                          ├─ L2 中风险（标准审 + WIP=10）        │
                          └─ L3 高风险（专家审 + WIP=3）         │
                                             │
                              WIP ≤ 利特尔法则上限
                              （周期时间 × 吞吐量）
```

**拉式机制**：模块完成 → WIP 计数 -1 → 下一卡自动入审（不等人推送）。这天然适配 AI 持续生成的特性。

> **本节回答**：本节属于流层——给上层"质量涌现"提供执行节奏，给下层"声明式控制"提供反馈来源。

## 第 6 部分：控制视角（MDM 声明式 + Harness 工程）

### 6.1 命令式 → 声明式的范式跃迁（核心哲学跃迁）

| 范式 | 形态 | 代价 |
|---|---|---|
| 命令式（v2 状态机） | 人决定何时迁移 | 人成为瓶颈 |
| 声明式（v3 范式跃迁） | manifest 声明期望，系统持续 reconciliation | 一次设计、永久运行 |

这是 v3 相对 v2 最深的范式跃迁——治理从"人在决策环路里"变成"人在期望状态定义环路里"。

### 6.2 Apple DDM 2024+ 的三要素

| 要素 | 定义 | 实现 |
|---|---|---|
| Declaration | 管理者定义的 desired state manifest | Configurations + Assets + Activations + Predicates |
| Reconciliation | 设备拉取 manifest 并自动收敛 | 异步 pull + 自检 + 修正 |
| Convergence | 持续强制：断网仍维持期望状态 | Status channels 主动上报 |

### 6.3 Apple DDM ↔ Kubernetes ↔ 模块治理三方对照

| 维度 | Apple DDM | Kubernetes | 软件模块治理 |
|---|---|---|---|
| 期望状态载体 | Declarations | CRDs | module.yaml + manifest |
| 拉取机制 | Device pulls | Controller watches | Reconciliation agent |
| 条件应用 | Predicates | Label selectors | 信号阈值 |
| 状态报告 | Status channels | Status subresources | 健康度三维评分 |
| 故障下行为 | Offline 自维持 | Controller 重启幂等 | 软删窗口 + 墓碑 |

**核心洞察**：三者本质同构——都是"声明 + 持续 reconciliation"。模块治理不需要发明新范式，只需借用成熟范式。

### 6.4 模块的 desired state manifest（字段模板）

```yaml
module:
  name: order-service
  domain: core/order

intent:
  intent_id: INT-2026-001
  business_signal_threshold:
    active_demands: ">= 1"
    contract_subscribers: ">= 1"

contracts:
  exposed: [order-api-v1]
  consumed: [payment-gateway-v2]

quality:
  test_coverage: ">= 80%"
  archtest_compliance: required

lifecycle:
  current_state: asset
  health_thresholds:
    value_score: ">= 60"
    structure_score: ">= 60"
    engineering_score: ">= 60"
  retirement_window: "24h soft-delete"
```

### 6.5 Reconciliation Loop（伪代码）

```
loop:
    1. pull module manifests from registry
    2. collect signals (CI / git / dependency graph / traffic)
    3. compute current health score (三维)
    4. detect drift (current vs desired)
    5. propose remediation, 按可逆性 R1-R5 让渡：
         R1 (实验代码): AI 直接执行
         R2-R3 (跨域影响): AI 提议 + 人审批
         R4-R5 (生产/资金): 阻塞 + 强制人决策
    6. report status to dashboard
```

### 6.6 Harness 五件套（基于 Anthropic 官方）

| 组件 | Anthropic 实现 | 治理含义 | 自主权梯度对应 |
|---|---|---|---|
| 系统上下文 | 动态组装条件型指令集 | 注入项目知识、约束、规范 | L0 起 |
| 工具约束 | fail-closed 权限 + 命令黑名单 | 限定 AI 能用什么 | L0 起，逐级放权 |
| 上下文注入 | Agent Skills + Progressive Disclosure | 按需加载知识 | L1 起 |
| 记忆与进度 | Feature lists + git commits | 跨 session 状态保持 | L1 起 |
| 评估循环 | 端到端测试自动化 | 持续收敛而非一次推理 | L0 必须 |

**本质**：从一次性 prompt → 持续运行环境。Harness 工程不是 prompt engineering 的升级，是质变。

### 6.7 自主权梯度的 Harness 配置（具体差异）

| 自主级别 | Harness 配置 | 可执行可逆性范围 |
|---|---|---|
| L0 只读 | 仅上下文 + 评估 | – |
| L1 本地修改 | + 受限文件编辑工具 | R1 |
| L2 受控外部 | + 需批准的外部 API、git push | R1-R2 |
| L3 跨域写权限 | + 跨域写权限 | R1-R3 |
| 永不放开 | – | R4-R5 |

### 6.8 Harness + DDM 的统一（v3 最深合流）

```
        ┌──────── 期望状态（desired state manifest）────────┐
        │     由人定义意图、契约、约束、健康阈值              │
        └────────────────────┬───────────────────────────────┘
                             ▼
        ┌──────────────────────────────────────────────────┐
        │           Reconciliation Loop（持续收敛）         │
        │                                                  │
        │   ┌──────────┐         ┌────────────────────┐    │
        │   │ 信号采集 │ ◄─────► │  Harness 五件套     │    │
        │   │ (机械化) │         │  · 系统上下文       │    │
        │   └──────────┘         │  · 工具约束         │    │
        │         │              │  · 上下文注入       │    │
        │         ▼              │  · 记忆与进度       │    │
        │   ┌──────────┐         │  · 评估循环         │    │
        │   │  判定    │         └────────────────────┘    │
        │   │  drift   │                  │                │
        │   └────┬─────┘                  │                │
        │        ▼                        ▼                │
        │   ┌─────────────────────────────────┐            │
        │   │   执行修正（按可逆性 R1-R5）     │            │
        │   └─────────────────────────────────┘            │
        └──────────────────────────────────────────────────┘
                             │
                             ▼
                       现实状态收敛
```

**核心命题**：Harness + DDM = **环境级反馈控制系统**。两者本质同构，都是从"命令式单次干预"转向"声明式持续收敛"。这是整个 Vibe Coding 治理的底层哲学跃迁，是 v3 相对 v2 最深的理论合流。

> **本节回答**：本节属于控制层——给整个治理体系一个**自动化的运行时**，让流层的反馈能闭环。

## 第 7 部分：双重实体模型

### 7.1 框架（不变资本）的四个职能

| 职能 | 内容 | 失守代价 |
|---|---|---|
| 领域隔离 | 限界上下文的物理边界 | 模块互相绞缠，重构成本随时间二次方上升 |
| 基础抽象 | 存储/消息/鉴权/观测 的统一接口 | 适配器膨胀、依赖混乱 |
| 契约骨架 | API/事件/错误码的标准形态 | 模块间无法协同 |
| 质量基底 | 测试基类/Mock/沙箱/架构约束 | 每个模块重复造轮子 |

### 7.2 模块（产出物）的五态机 + 信号清单

模块就是在框架机床上批量冲压的产品，必须携带：

- **身份**：唯一名、所属领域、对外契约
- **意图**：创建动机、业务关联
- **状态**：experimental / candidate / asset / maintenance / retired
- **信号**：业务、架构、工程三维健康度（机械化采集，详见 8.3）

### 7.3 双向反馈环

```
   框架（季度演进）
         │
         ▼
   模块批量冲压（周演进）
         │
         ▼
   模块失败模式 + 共性需求
         │
         ▼
   驱动框架演进（回到顶部）
```

**节奏**：框架是慢变量（季度），模块是快变量（周）。两者通过失败模式与共性需求形成正向反馈。

> **本节回答**：本节属于综合层——把第 3 部分的资本论 C/V 落到具体可见的双实体。

## 第 8 部分：模块生命周期（声明式治理的具象）

### 8.1 五态机

```
意图 → experimental → candidate → asset → maintenance → retired
              ↓回退        ↓回退       ↓
              ←──── 不达标 ────┘       └→ 墓碑 (24h 软删)
```

### 8.2 desired state manifest

字段模板见 6.4。每个模块都必须有完整 manifest，否则 reconciliation 拒绝管理（"manifest 即 single source of truth"）。

### 8.3 信号采集（机械化清单）

| 维度 | 信号 | 采集方式 |
|---|---|---|
| 业务（价值锚定） | 关联活跃需求数 / 契约订阅数 / 流量触达 | 需求系统 API + 流量埋点 |
| 架构（边界封控） | 框架使用合规度 / 跨域依赖数 / 契约注册一致性 | 静态分析 + archtest |
| 工程（制程内建） | 测试覆盖率 / 构建通过率 / 缺陷密度 / 活跃度衰减加权 | CI + git + 缺陷追踪 |

**绝对禁止**：靠人手填写信号。所有信号必须是机械化采集的衍生量。

### 8.4 状态迁移 + 回退路径 + 墓碑

| 迁移 | 入口条件 | 回退路径 |
|---|---|---|
| 意图 → experimental | 意图通过价值评审 | 删骨架 + 关意图 |
| experimental → candidate | 业务信号 ≥ 阈值 + 冒烟通过 | 退回 experimental |
| candidate → asset | 全门禁通过 + 人审批 | 退回 candidate |
| asset → maintenance | 业务信号衰减但仍有依赖 | 重新激活回 asset |
| maintenance → retired | 无依赖 + 业务信号归零 | 24h 内可恢复 |

**墓碑字段**：模块名 / 最后版本 / 对外契约快照 / 依赖快照 / 退役原因 / 退役日期 / 24h 软删窗口。墓碑是"可审计的死亡证明"，不是简单一行日志。

### 8.5 健康度三维评分（公式）

```
价值得分 = w1·关联需求数 + w2·契约订阅数 + w3·流量得分    (0-100)
结构得分 = w1·框架合规 + w2·边界一致性 + w3·契约注册一致   (0-100)
工程得分 = w1·覆盖率 + w2·构建通过率 + w3·活跃度衰减加权    (0-100)
```

**衍生信号**：
- 健康警告：任一维 < 30
- 强制退役建议：任一维 < 10
- 强制人审：三维全 < 50 持续两周

**北极星指标**：资产健康率 = 三维全 ≥ 60 的资产数 / 全部资产数（详见第 12 部分）。

> **本节回答**：本节把第 6 部分的声明式范式落到具体的字段、信号、公式。

## 第 9 部分：渐进式实施路径（四阶段 × 七视角）

### 阶段一：显式治理（1-2 月）

**入口**：组织有 AI 编码使用，但缺差异化治理。

**七视角应用**：

- **第一性原理证**：F1+F2 推出"必须先建机床（框架）"，F4 推出"必须显式标记资产"
- **金字塔顶结论**：让所有模块"被需要、被信任、被理解"的初始可见性建立
- **资本论判断（C/V/M）**：C 投入大（锻造框架），V 投入中（标记模块），M 期望低（治理建立但未收益）
- **V-model 形态**：左侧仅意图 + 编码，右侧 CI + 安全扫描
- **DevOps + DORA 节奏**：DORA 基线建立，不必达标
- **看板成熟度**：双环看板上线，无 WIP 限制
- **声明式程度**：module.yaml 起步，reconciliation 全人工
- **Harness 五件套配置**：L0 只读 + 评估循环，仅给 AI 上下文与评估

**出口/晋阶门**：
- 100% 模块完成 module.yaml 标记
- 差异化 CI 门禁运行 ≥ 30 天且通过率稳定
- 至少 2 次人工晋升仪式完成

**KPI**：
- 治理覆盖率 ≥ 95%
- 门禁有效性 ≥ 5%（拦截真实问题占比）

**主要风险与对策**：
- 框架建设拖延 → 用最小可行框架（仅领域边界 + 契约骨架）启动
- 模块标记流于形式 → 接 CI 校验，无 module.yaml 不允许构建

---

### 阶段二：辅助判断（2-4 月）

**入口**：阶段一稳定 ≥ 1 个月，AI Agent 运行的最小基础设施就位。

**七视角应用**：

- **第一性原理证**：F1+F2 推出"必须把审查负担转给 AI 初筛"
- **金字塔顶结论**：让"被需要"信号通过 AI 自动放大
- **资本论判断（C/V/M）**：C 投入小（Agent 部署），V 投入主要在审批者，M 开始显现（监督劳动自动化）
- **V-model 形态**：右侧加入契约校验 + 自动化测试覆盖率门禁
- **DevOps + DORA 节奏**：Lead Time 开始有目标值
- **看板成熟度**：候选态引入，分层快速通道初步上线
- **声明式程度**：manifest 字段开始用于 Agent 决策（信号阈值开始 reconciliation）
- **Harness 五件套配置**：L1 本地修改（受限文件编辑） + 健康度报告生成

**出口/晋阶门**：
- AI 建议接受率 ≥ 70%
- 候选态机制运行 ≥ 1 个月，未出现"绕过候选态成为资产"

**KPI**：
- AI 建议接受率 70-90%
- 误警率 < 30%
- 平均状态迁移决策耗时显著下降

**主要风险与对策**：
- 审批疲劳 → 健康度报告分桶（必看 ≤ 5 条/周）
- AI 证据不足 → 强制 Agent 输出三维信号原始数据

---

### 阶段三：有限自治（4-8 月）

**入口**：阶段二 AI 建议接受率稳定 ≥ 80%，回滚机制经历至少一次真实失败演练。

**七视角应用**：

- **第一性原理证**：F1 推出"在 R1-R3 可逆区释放 AI 自主"，F3 推出"自动退役机制对抗资产腐烂"
- **金字塔顶结论**：实验模块全自动闭环
- **资本论判断（C/V/M）**：C 持续优化（框架自演进试点），V 大幅释放，M 显著扩张（自动养护资产）
- **V-model 形态**：右侧加入形式化验证 + 模糊测试 + e2e 全链路
- **DevOps + DORA 节奏**：高性能水位达成（日多部署 + Lead Time <1 天 + Failure Rate <5%）
- **看板成熟度**：拉式系统全自动，分层快速通道按风险动态调度
- **声明式程度**：reconciliation 在 R1-R3 区域自治；manifest 成为唯一真实状态源
- **Harness 五件套配置**：L2 受控外部（需批准的 API + git push） → 实验模块的生灭全自动

**出口/晋阶门**：
- 实验模块全自动闭环 ≥ 3 个月零误删
- candidate → asset 强化审批流程稳定

**KPI**：
- 实验模块流转效率（创建到退役中位耗时）下降 50%
- 自动退役回滚率 < 1%
- 资产平均健康度持续上升

**主要风险与对策**：
- 实验模块自动繁殖泛滥 → 意图解包 Agent 孵化提案数量按 WIP 调控
- 寿命包参数误退役 → 阈值由历史数据校准，不允许凭直觉

---

### 阶段四：完整自治（远景，不承诺时间表）

**入口（任一未达不进入）**：
- 阶段三连续运行 ≥ 6 个月零重大事故
- 行业出现成熟的 AI 决策可解释/可审计技术
- 组织已建立独立的 AI 决策审计员角色

**七视角应用**（仅作方向）：

- **第一性原理证**：F4 推出"R5 永不放开"作为永恒边界
- **资本论判断**：C 自演进（框架内非破坏变更由 AI 主导），人完全转向"边界维护者"
- **声明式程度**：策略模型替代规则引擎；manifest 由历史决策训练而成
- **Harness 五件套配置**：L3 跨域写权限 + 三熔断（安全/战略/伦理）

**关键约束**：R5 级动作（影响用户/资金/物理设备）永不进入此阶段。

**KPI**：自主决策一致性 / 熔断触发率（应稳定，不应频繁）。

**为什么不承诺时间表**：依赖技术突破与组织信任的双重成熟。把它写为路线图条款会让阶段三过早收尾。

> **本节回答**：本节是综合落地层——证明前 8 节的理论能从 0 走到完整自治。

## 第 10 部分：角色与组织演化

### 10.1 资本论视角下的劳动力流向

AI 自主度提升 = V 被 C 替代。释放的 V 必须流向更高价值区域，否则就是"被替代"而非"被解放"。

| 阶段 | 释放的 V | 应流向的高价值 V |
|---|---|---|
| 一 | 模块标记的人工劳动 | 框架建筑 / 规则制定 |
| 二 | 巡检与初筛 | 健康度模型设计 |
| 三 | 实验模块运维 | 寿命规则设计 / 回滚机制设计 |
| 四 | 大量审批劳动 | 战略 / 安全 / 伦理守门 |

### 10.2 角色变化矩阵

| 阶段 | 架构师 | 开发工程师 | 新增角色 |
|---|---|---|---|
| 一 | 框架建筑师 | 业务编码 + 晋升仪式 | – |
| 二 | 健康度模型设计者 | AI 建议复核 | AI Agent 调优工程师 |
| 三 | 寿命/回滚机制设计 | 资产审批 + 异常处理 | **AI 决策审计员** |
| 四 | 框架宪法守护者 | 三熔断守门人 | AI 行为研究员 |

### 10.3 AI 决策审计员的独立性

**关键原则**：AI 决策审计员必须独立于 AI Agent 调优工程师——避免裁判员兼运动员。这是阶段三才能进入的独立角色。

> **本节回答**：本节属于综合层——确保 V 不被 C 直接吞噬，而是迁移到更高 V。

## 第 11 部分：反模式与适用边界

### 11.1 本方案不解决的问题

- **业务方向错误**：再好的治理也救不了"用正确的方式做错的事"
- **组织协作问题**：本方案治理的是制品，不是会议、流程、人际
- **创意性工作**：研究/探索/创新代码无法重武装

### 11.2 七大反模式（每一个都是真实陷阱）

| 反模式 | 症状 | 矫正 |
|---|---|---|
| 治理过度 | 实验模块也跑全门禁 | 严格分级，宁宽勿一刀切 |
| 信号填空 | 让人手填业务信号 | 必须机械化采集 |
| AI 建议崇拜 | 接受率 100% 否决率 0% | 健康否决率下限 ≥ 10% |
| 状态机僵化 | 模块卡某态半年不动 | 加"超期未迁移"告警 |
| 框架沦为容器 | 不强制约束 | 框架使用本身门禁化 |
| 审批仪式化 | 不看证据点同意 | 强制勾选证据已查验 |
| 治理 ROI 倒挂 | 治理时间 > 编码时间 30% | 暂停推进，重审边界 |

### 11.3 何时停止推进

任一信号出现，停在当前阶段而非推进：
- 治理活动 > 30% 工程师时间持续两季度
- 误警率 / 误退役率持续高于目标
- 团队 < 10 人且模块 < 30（治理收益不抵成本）

> **本节回答**：本节属于边界层——明确本方案的失效条件。

## 第 12 部分：度量框架

### 12.1 北极星指标

> **资产健康率** = 三维健康度全 ≥ 60 的资产模块数 / 全部资产模块数

这是单一最值得追踪的指标——同时反映价值/结构/工程三支柱的状态。

### 12.2 各阶段次级指标

| 阶段 | 次级指标 |
|---|---|

| 三 | 流转效率 / 自动退役回滚率 / 资产健康度趋势 |
| 四 | 自主决策一致性 / 熔断触发率 |

### 12.3 DORA 五指标的接入

| DORA 指标 | 治理含义 |
|---|---|
| Deployment Frequency | 模块迁移流速 |
| Lead Time | 单模块端到端工程效率 |
| Change Failure Rate | 治理质量 |
| Recovery Time | 回滚机制有效性 |
| Rework Rate | 文档/manifest 质量 |

### 12.4 季度评审节奏（对方案本身的治理）

每季度对方案本身进行评审：
- 哪些信号被证明无效？
- 哪些门禁拦截的全是误报？
- 哪些状态迁移规则让团队感到僵化？

**方案本身也要进入治理** —— 方法论不能成为不可触碰的圣物。

> **本节回答**：本节属于度量层——给整个方案一个可测的、可批判的对外接口。

## 第 13 部分：结语

### 一句话总纲

> **用第一性原理推导出三公理三支柱；用框架锚定边界、用声明式 manifest 管理生命周期、用 Harness 工程让渡 AI 自主权、用看板吸收 AI 产能冲击；用资本论分析价值流向，用 DORA 度量执行节奏 —— 使 AI 加速产出的同时，让组织对产物始终保持需要、信任、理解。**

### 七视角的统一图景

第一性原理推导出来的"对抗三衰减"目标，由资本论指明价值流向，由 V-model + DevOps + 看板提供生命周期与节奏，由 MDM 声明式 + Harness 工程提供执行外壳，由金字塔法则保证整个推理链条可读。

七个思想不是平行陈列，是分层递进——一切都从 4 条不可再分事实出发，沿"事实 → 公理 → 支柱 → 机制 → 阶段"五层向下落地。

### 最终命题

**AI 是劳动力倍增器，不是新的价值源泉**。让 AI 能加速产出而不让组织失去对资产的把握，是这个时代软件工程的根本命题——本方案给出一个完整答案。
